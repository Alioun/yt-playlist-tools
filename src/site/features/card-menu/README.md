# Right-click card menu

`cardMenuFeature` is the `card-menu` FeatureHost definition for www. Its `start` receives the qualified feature Scope, the current-view reader and three concrete services: the page `document`, PageLink's `run` and `state`, and a `notice.request(due)` collaborator. Nothing is allocated before `start`. Start installs one capture `contextmenu` listener on the document through the Scope and one view subscription. Switching off, revocation and host disposal dispose the Scope, which removes both. The listener reads the current view on every event, so `keepLinkMenu` changes apply without a restart.

`decideCardMenu` decides synchronously, before any cancellation. It keeps the browser menu for an already-cancelled event, Shift, a revoked view, a not-working status, a PageLink that is not `ready`, anything Items' `recogniseWwwItem` does not report as a supported pointed card (ads, playlists, mixes, channels, posts, unrecognised items, players, ordinary page), a detached or foreign-document renderer, any link in the event's composed path that does not point at the card's own video, channel-name and avatar parts inside the card, the card's own thumbnail and title links when `keepLinkMenu` is on, and a card whose own menu button is missing, disabled or hidden. The composed path is the authority. Pointer is not consulted.

One case reads the page instead of the path. On search results and the home grid, YouTube's hover preview sits above its card from another part of the page, so a right-click on it has no card in its path. When Items names any element of the path a preview, the decision reads `document.elementsFromPoint` at the event's point. It takes the first element outside the preview, with that element's ancestors, as the path. Every rule above then applies to what the preview covers. The links rule also applies to the preview's own part of the event's path. The playing preview on search shows an "Includes paid promotion" link to Google's help pages, and a right-click on it keeps the browser menu. The preview's own link to its video counts as the card's video link. The whole path is tested because Perchling draws its own thumbnail buttons inside the playing preview. Such a button is in its own shadow tree, so only its host reads as a preview.

The open decision carries the point where the menu opens. That is the event's point when the browser's own hit test there, `document.elementsFromPoint`, finds a part of the card. A pointer always passes, because that hit test picked the right-click's target. A menu opened from the keyboard has no pointer, and the browser reports a point of its own. Chromium reports the middle of the focused element, which passes too. When the hit test finds no part of the card, such as at the window's corner, the menu opens at the middle of the card's own menu button.

The decision does not compare the point with element boxes. On live YouTube a pointer hits a card on pixels outside the box of the card and of every part between the hit part and the card. A sweep on 2026-11-22 found 406 such points among 48781 on the home grid and 376 among 28224 on the watch sidebar. On the home grid they are the top pixel row of cards whose box starts at a fraction of a pixel.

The menu-button proof walks `cardMenuButtons` from `src/shared/youtube/card-menu-buttons.ts`, the same table the gateway adapter's `openMenu` clicks from, and takes the first connected match. If Items assigns that button to a different card, the browser menu is kept, so the gateway is never asked to click another card's button. Only after every check passes does the listener call `preventDefault` and request `{ job: { kind: "openCardMenu", videoId, at } }` targeted at that renderer, with the video Items recognised at the right-click and the decision's point. The gateway refuses to click when the renderer has since been recycled to show a different video. The listener does not stop propagation and never dispatches a synthetic event. The job's result is ignored. When the page-side click fails, refuses or cannot confirm, the feature does nothing more: no toast, no retry, no notice. The browser's menu cannot be brought back, a native limitation recorded in the audit report.

The feature needs no account. It sends no account pin and reads no account, setup, filter or membership field, and it never calls AddFlow. When the view marks the card menu not working, it keeps the browser menu and asks `notice.request` once for the due notice that names `card-menu`. The request is re-armed when that notice is no longer due. The core's `NoticeOwner` and plain presenter in `src/site/core/notice/` own presentation, copy and acknowledgment. A request callback is not a storage or Monitor receipt. SiteCore assembly, which binds the request to the owner with localized copy and acknowledgment, is adjoining work.

The module imports Items recognition and its `linkedVideo` link rule, Scope (through Items), shared validation and the shared menu-button table as values. Everything else is type-only. It loads no kit, toaster, Svelte runtime, picker or notice presenter.

The behavior tests live beside the feature in `card-menu.bun-test.ts`. The harness, consumer, type negatives, controls and future gates live in `tools/fixtures/site-card-menu/`. The tests, consumer and type negatives run. The mutation controls and type probes in `controls.json` and `type-probes.json` pin an older source identity and have not run. Native browser menus, real YouTube markup and isolated-world behavior remain unproven.
